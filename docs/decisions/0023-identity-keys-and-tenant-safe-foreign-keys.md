# 0023 — Identity keys, timestamps, and tenant-safe foreign keys

- **Status:** Accepted — **verified empirically 2026-09-22**
- **Date:** 2026-09-22

> **Verified (2026-09-22)** by a throwaway isolation spike against PostgreSQL 17 and Prisma 7.10.0.
> Recorded here because the Decision below left two things as instructions rather than facts.
>
> - `@default(uuid(7))` **is** supported. The open question in §3 is closed; use it, no `uuidv7`
>   package needed.
> - Composite foreign keys generate exactly as intended —
>   `FOREIGN KEY ("orgId","ticketId") REFERENCES "Ticket"("orgId", id)` — and a cross-tenant reference
>   is rejected with `P2003 / Comment_orgId_ticketId_fkey`, while a same-tenant one succeeds.
> - **The counterfactual was reproduced.** With a single-column FK on `ticketId`, the same insert
>   *succeeded*: a row carrying org B's `orgId` was written pointing at org A's ticket, past `WITH CHECK`
>   and past RLS. The hole this ADR exists to close is real, not theoretical.
> - `@db.Timestamptz(3)` produces zero `timestamp without time zone` columns.
>
> One correction to the environment this assumes: **Prisma 7 removed `url` from the datasource block.**
> Connection strings live in `prisma.config.ts`, the client takes a driver adapter
> (`@prisma/adapter-pg`), and the generator provider is now `prisma-client`, not `prisma-client-js`.
> Two adapters give the two roles two independent pools, which suits the design better than the old
> single-URL model did.
- **Refines:** [0015](0015-tenant-isolation-rls.md) — adds the structural layer the four-layer model was missing

## Context

`ARCHITECTURE.md` asserted three things about physical schema that had no mechanism behind them: ids are
UUID v7, timestamps are UTC, and every tenant-owned table carries `orgId`. Working through each turned up
a defect, and the third turned up the largest hole in the isolation design.

**Foreign keys bypass Row-Level Security.** PostgreSQL performs referential-integrity checks with the
privileges of the referenced table's owner and with row security *disabled* — this is documented,
deliberate behaviour that exists so that constraints cannot be silently broken by a policy. The
consequence for a shared-schema multi-tenant design is severe:

```sql
-- connected as patchgrid_app, with app.current_org_id = <org B>
INSERT INTO "Comment" ("orgId", "ticketId", "authorId", body, visibility)
VALUES ('<org B>', '<a ticket id belonging to org A>', '<me>', 'hello', 'PUBLIC');
```

The FK check on `ticketId → Ticket(id)` passes, because RI ignores RLS. `WITH CHECK` on `Comment` passes,
because the row's own `orgId` is org B's. **The row is written.** No layer objects: every individual row
is correctly tenanted, and the relationship between them is not something any policy examines. The result
is a comment in one tenant attached to another tenant's ticket — an orphan in the UI, a leak through any
join written in raw SQL, and an existence oracle (FK success vs. violation tells you which ticket ids
exist elsewhere).

A second, related hole: people are referenced by `User.id`. `User` is platform class with no policy and
no `orgId`, so nothing — not RLS, not a composite key — prevents `Ticket.assigneeId` pointing at an
employee of a different company. "The assignee is a member of this org" was an application-layer hope.

## Options considered

**Cross-tenant references**

1. **Application-layer validation** — check the parent's `orgId` before every insert. Correct when
   written, absent when forgotten, and invisible in review because the absence looks like nothing.
2. **Triggers** — a `BEFORE INSERT` trigger per child table comparing `orgId` against the parent.
   Works, but it is thirty triggers of hand-written PL/pgSQL, it costs a lookup per write, and a trigger
   that is dropped by a future migration fails silently.
3. **Composite foreign keys on `(orgId, id)`** — the reference itself carries the tenant, so a
   cross-tenant reference is not rejected, it is *unrepresentable*. No runtime cost beyond a wider index,
   no code, nothing to forget.

**People references**

1. **Keep `userId`** and validate membership in services. Same failure mode as above.
2. **Reference `Membership`**, which is tenant-owned and therefore composite-FK-able. Membership in the
   org becomes a property of the key rather than a property of the code.

**Identifiers**

PostgreSQL 17 has no native `uuidv7()` (it arrives in 18), so v7 must be generated by the application or
abandoned for `gen_random_uuid()` (v4). v4 scatters inserts across the whole B-tree, causing page splits
and write amplification on every index; v7's time prefix keeps inserts at the right edge and makes
`(orgId, createdAt DESC, id DESC)` cursors monotonic, which the pagination design depends on.

**Timestamps**

Prisma maps `DateTime` to `timestamp(3)` — *without* time zone — by default. Every SLA comparison,
`pausedAt` arithmetic and `now() >= resolveBy` in the scanner would then depend on the session `TimeZone`
of whichever connection ran it.

## Decision

### 1. Composite foreign keys between tenant-owned tables

Every tenant-owned parent declares `@@unique([orgId, id])`. Every tenant-owned child references the pair:

```prisma
model Ticket {
  id    String @id @db.Uuid
  orgId String @db.Uuid
  // …
  @@unique([orgId, id])                 // legal target for a composite FK
}

model Comment {
  id       String @id @db.Uuid
  orgId    String @db.Uuid
  ticketId String @db.Uuid
  ticket   Ticket @relation(fields: [orgId, ticketId], references: [orgId, id])
  // …
}
```

Applies to every FK where both ends are tenant-owned: `Comment`, `Attachment`, `TicketLink` (both ends),
`TicketAsset`, `TicketWatcher`, `ProblemDetails`, `ChangeDetails`, `ChangeApproval`, `Category.parentId`,
`Category.defaultTeamId`, `Ticket.categoryId`, `Ticket.teamId`, `Ticket.slaPolicyId`,
`TeamMembership` (ADR-0025), `Team.leadMembershipId`, `Invitation.teamId`, `Notification.ticketId`,
`KnowledgeArticle.categoryId`, `ApiToken.membershipId`, and every later table keyed by `ticketId`
(`TicketTriage`, `TicketEmbedding`, `PhishingReport`, `InboundEmail.ticketId`).

### 2. People are referenced by `Membership`, not `User`

| Was | Becomes |
| --- | --- |
| `Ticket.requesterId`, `Ticket.assigneeId` | `requesterMembershipId`, `assigneeMembershipId` |
| `Comment.authorId` | `authorMembershipId?` + `authorKind: MEMBER \| SERVICE \| SYSTEM \| AUTOMATION` |
| `TicketWatcher.userId`, `addedById` | `membershipId`, `addedByMembershipId` |
| `ChangeApproval.approverId` | `approverMembershipId` |
| `Asset.ownerId` | `ownerMembershipId?` |
| `KnowledgeArticle.authorId` | `authorMembershipId` |
| `Attachment.uploadedById`, `Invitation.invitedById`, `ApiToken.createdById`, `TicketTriage.decidedById` | `…MembershipId` |
| `AuditLog.actorId?` | `actorKind: MEMBER \| SERVICE \| SYSTEM \| PLATFORM` + `actorMembershipId?` + `actorPlatformAdminId?` |
| `Notification.userId` | keeps `userId` (delivery is to a person) **and** gains `membershipId` |

`Membership` gains `displayName` and `avatarUrl`, denormalised from `User` and refreshed when the user
updates their profile. Hot list queries then render names without joining the one table in the database
where a forgotten `where` clause would expose every customer's employees. It also gives departed and
pseudonymised users a stable display ("Former member") without a nullable join.

`Membership.userId` remains, so "who is this really" is one hop away, and `RefreshToken`,
`PasswordResetToken`, `EmailVerification` and `PlatformAdmin` continue to reference `User` directly —
they are platform-class by nature.

### 3. Identifiers

- Every id is UUID v7, typed `String @db.Uuid` in Prisma and `uuid` in Postgres — never `text`, because
  the RLS policies compare against `current_setting(…)::uuid` and a `text` column would neither match
  nor use its index.
- Generation is application-side. **Verify whether the pinned Prisma version supports
  `@default(uuid(7))`; if it does not, generate in the repository layer with the `uuidv7` package.**
  `@default(uuid())` (v4) and `dbgenerated("gen_random_uuid()")` are banned by ESLint.
- Ids are **not secrets.** They are time-ordered and partially predictable by design. No authorization
  decision anywhere may depend on an id being unguessable.

### 4. Timestamps

Every datetime column is `@db.Timestamptz(3)`. Both connection strings carry `TimeZone=UTC`. The wire
format is ISO-8601 with an explicit offset.

### 5. Enforcement in CI

Four introspection assertions, run as their own CI job so a failure names the actual problem:

1. Every FK whose two endpoints are both tenant-owned is composite and includes `orgId`.
2. `information_schema.columns` contains zero `timestamp without time zone` columns.
3. Every `id` and every `*Id` column on a tenant-owned table has `udt_name = 'uuid'`.
4. Every tenant-owned table is `SELECT`-able by `patchgrid_app` (`has_table_privilege`) — catching the
   missing-`GRANT` failure mode from `ENGINEERING.md`.

These join the existing RLS-coverage check as part of the tenancy gate.

## Consequences

- **Two whole classes of bug move from "caught by a test if we wrote one" to "rejected by the
  database".** Cross-tenant references and non-member assignees become unrepresentable rather than
  unlikely. This is the structural layer the four-layer model in ADR-0015 was missing; call it layer 0,
  because it runs before any of the others get a chance to be wrong.
- Indexes get wider (`(orgId, id)` instead of `(id)`). On a tenant-filtered workload this is neutral to
  positive — `orgId` leads every index already, by the same reasoning.
- Prisma relation declarations are more verbose. Accepted; the verbosity is the constraint being visible.
- Every query that renders a person now joins `Membership`, not `User`, and usually not at all thanks to
  `displayName`. `User` becomes a table the application reads almost exclusively during authentication.
- `Membership.displayName` can go stale if a user renames themselves. Refreshed on profile update inside
  `runAsTenant` per membership; reconciled by the same nightly job as ADR-0022's projections.
- Writing a `Comment` now requires the ticket's `orgId` in hand — which the repository has anyway, since
  every repository method takes an explicit `orgId` (ADR-0015 layer 2). The two rules reinforce each
  other rather than adding work.
- Migration path if reversed: dropping to single-column FKs is a mechanical, non-destructive migration.
  Nothing here is a one-way door except the habit.
