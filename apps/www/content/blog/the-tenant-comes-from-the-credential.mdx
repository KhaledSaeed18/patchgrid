Every request to Patchgrid's API arrives at `api.patchgrid.xyz`, and that host name does not say which tenant the request is for. Our first design assumed it would. Fixing that meant deciding where the tenant should come from instead. The answer is the credential, meaning the session token or API token the caller presents, with the `Origin` header used to cross-check it. This post walks through that decision and what follows from it, down to one boolean argument passed to PostgreSQL.

## The design that did not work

Patchgrid gives each tenant its own subdomain, such as `acme.patchgrid.xyz`. The early docs described tenant resolution on the API as "host → slug → Organization", and the threat model compared "the host's organization against the token's `org`".

That cannot work. There is no `acme.api.patchgrid.xyz`, only `api.patchgrid.xyz`, so there is no slug in the host to parse. ADR-0014 tried resolving the tenant from `Origin` or `Referer` instead. But under ADR-0007, Next.js server components call the API directly, and a server-to-server `fetch` sends no `Origin` at all. That covers most page loads, not a rare case. API tokens used from a script have no meaningful `Origin` either.

ADR-0024 lists the options. Parsing the host is impossible. Using `Origin` alone breaks server rendering and integrations. The third option is to read the tenant from the one thing every caller already presents: its credential. The ADR puts it like this: **the credential carries the tenant; the host is corroboration.** The earlier docs had this backwards, and three files depended on the inversion.

## The resolution order

The API resolves the tenant once per request, in this order:

1. `Authorization: Bearer pg_…` → the tenant is the API token's org. Cookies are ignored entirely.
2. Otherwise, the access-token cookie's `orgId` is the tenant.
3. If `Origin` is present, it must resolve to that same org, or the request gets `403`. This is the CSRF and cookie-tossing check, not how the tenant is chosen.
4. If `Origin` is absent (a server-side call), `X-Patchgrid-Tenant: <slug>` must be present and must match. It is a consistency check, never trusted on its own: a request with only this header and no valid token is unauthenticated.
5. Routes marked `@TenantOptional` skip all of the above.

The resolver uses the asserted workspace only to pick which cookie to read, then requires the cookie's own claim to agree:

```ts
// The cookie was named by `slug`; its claim must agree. A tossed, forged or
// stale cookie does not, and never selects the tenant (ADR-0024 §2–3).
if (org.slug !== slug) {
  return refuse("tenant-mismatch", "The session belongs to a different workspace")
}
```

The consequence for the rest of the API is simple: **the tenant is never a request parameter.** `ENGINEERING.md` treats any endpoint that accepts an `orgId` in a body or query string as a bug. The only exceptions are the tenant-less auth and provisioning routes, which are explicitly marked. Authorization never looks at `orgId` either. By the time a permission is checked, the tenant is already settled, and the two layers stay separate.

One detail matters later. At this stage the cookie's claim has been *read* but not yet *verified*. Verification happens once, further down the request pipeline, in the auth guard. That is safe for choosing a tenant, because a forged claim gets the caller no more than an anonymous probe of a slug would. Whether it is safe for everything else that runs before verification is a separate question, and our security review found a case where it wasn't (finding 1 in the threat model's M9 section).

## One cookie per tenant

Subdomains were partly chosen so that two workspaces could be open in two tabs. The first cookie design undid that. It issued one session cookie on `Domain=.patchgrid.xyz` for every tenant. Our seed includes an account that belongs to two organizations, and with it the failure is deterministic. Tab A on `acme` holds an Acme token. Tab B on `globex` gets a `403`, goes through the org picker, and a Globex token is minted into the *same* cookie. Tab A's next request then fails, and the two tabs keep logging each other out.

ADR-0024 names the cookies per tenant instead:

```
pg_at_<slug>   access   Domain=.patchgrid.xyz  httpOnly  SameSite=Lax  Secure  Path=/
pg_rt_<slug>   refresh  Domain=.patchgrid.xyz  httpOnly  SameSite=Lax  Secure  Path=/api/v1/auth
pg_id          identity Domain=.patchgrid.xyz  httpOnly  SameSite=Lax  Secure  Path=/
```

Each tenant gets its own slot, so tabs on different tenants no longer collide. `pg_id` holds only the user's identity and gives no tenant access by itself. It is what the tenant-less `app.patchgrid.xyz` uses to list your workspaces. A cookie belonging to a different tenant is never used as a fallback; it is simply ignored.

We couldn't use the `__Host-` prefix, because it forbids a `Domain` attribute and `api.` has to read these cookies. That leaves a residual risk we record openly as R-1, cookie tossing. Anything that can set cookies on any `*.patchgrid.xyz` origin can overwrite `pg_at_<victim>`. Tokens are signed, so it cannot forge one, and the worst it can do is log a user out. Per-tenant names also mean an attacker cannot quietly switch *which* tenant a user is acting in, which would be the dangerous version of the attack.

## From a request to a row

Once the tenant is resolved, it goes into a request-scoped store. Every query then reaches PostgreSQL through a Prisma client extension that runs this as the first statement of its transaction:

```ts
/**
 * `true` makes the setting TRANSACTION-local. It must never become session-level
 * (`false`): pooled connections are shared between requests, and a session-level
 * tenant would leak into whichever request draws the connection next (ADR-0015).
 */
function setTenant(client: Pick<PrismaClient, "$queryRaw">, orgId: string) {
  return client.$queryRaw`SELECT set_config('app.current_org_id', ${orgId}, true)`
}
```

That third argument is the most important boolean in the codebase. The RLS policies read `app.current_org_id` to decide which rows exist. Connections come from a pool and are reused across requests. A session-level setting would stay on the connection after the transaction ends. The next request to draw that connection, possibly for a different tenant, would start with the previous tenant's id already set. A transaction-local setting disappears at commit or rollback, so it cannot outlive the work it was set for.

It also fails closed. Outside a transaction, the setting would last for one statement only. If the extension ever failed to open a transaction, RLS would see no tenant and return zero rows. The policy wraps the setting in `NULLIF(…, '')`, so an empty string filters everything too, instead of raising a cast error. If a tenant-owned model is queried with no tenant in context, the extension throws `NoTenantContextError` rather than running an unscoped query.

The one trap we hit is that Prisma promises are lazy. The extension runs when a query is *awaited*, not when it is called, so the tenant context must wrap the await: `run(ctx, async () => await fn())`, not `run(ctx, () => fn())`. Our isolation spike got this wrong on its first run. It failed closed with an error, which is the behaviour the design is meant to guarantee.

## Crossing tenants on purpose

Some work genuinely happens outside a single request's tenant: background jobs, provisioning, support sessions, the purge after a workspace is deleted. ADR-0015 originally proposed a `runAsPlatform` escape hatch. ADR-0022 then pointed out that this could not work, because the application role has no `BYPASSRLS`. With no tenant set, every policy evaluates to `NULL`. The escape hatch led nowhere.

Looking at the actual call sites showed that almost none of them needed a bypass. A job's payload already names its org. Provisioning knows the org it just created. Only three operations are truly cross-tenant: the org picker ("which workspaces am I in?"), accepting an invitation, and authenticating an API token. All three share one shape. A credential is presented and the tenant has to be discovered from it. That is a lookup problem, not an isolation problem. Two small platform-class projection tables, `UserOrgIndex` and `ApiTokenIndex`, answer the lookup. Invitation tokens carry their own org id.

That leaves two helpers with deliberately different names:

```ts
runAsTenant<T>(orgId: string, crossing: Crossing, fn: () => Promise<T>): Promise<T>
runAsPlatform<T>(crossing: Crossing, fn: () => Promise<T>): Promise<T>
```

`runAsTenant` is **not** a bypass. It points the ordinary mechanism at a known org: the extension sets `app.current_org_id`, RLS applies, and repositories behave exactly as they would in a request. Even the workspace purge runs this way, so RLS is still enforcing during the most destructive operation in the product. `runAsPlatform` runs with *no* tenant, so it can only reach platform-class tables. Both log the actor, the reason and where they came from, and both run their callback in a child context that hides the caller's tenant and any open transaction.

Which modules may import each helper is enforced by ESLint path rules, not by counting call sites. The API checks at boot that its own role lacks `BYPASSRLS` and refuses to start otherwise. ADR-0022 sums up the result: the application process holds no credential capable of reading another tenant's data.
